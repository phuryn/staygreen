# Deploying Staygreen

Staygreen is several services that work together: a dashboard, a database, sign-in, check runners in at least two regions, a status edge and three small Workers. There is no one-click install. Nearly every step is a command a coding agent can run with your providers' API tokens, though, so most of an installation is supervising one and checking each step before the next.

A copy is for running Staygreen for your own organizations: the [license](../LICENSE) (FSL-1.1-MIT) permits any use except offering it to others as a competing commercial product or service. Organizations still separate groups of people as they do on the hosted service. You don't need billing: from the next release, `SELF_HOSTED_PLAN=builder` on the app gives every workspace every Builder feature. Until then, a copy without Clerk Billing runs every workspace on the Free plan's limits, which `src/lib/plans.ts` sets.

Use separate development and production resources, and verify each boundary before accepting real monitoring traffic.

## What you need

| Part | Suggested resource | If omitted |
|---|---|---|
| Dashboard | Netlify on the free plan; `netlify.toml` and the two `netlify/edge-functions/` POST rate rules are supplied. Any Node 22+ host with Next.js App Router server actions and route handlers works | No member dashboard, configuration or agent API |
| Database | Supabase, a project on the Pro plan's Micro compute, in a region near your probes. The free plan does for a trial: 500 MB, no backups, and a project paused after a week without activity | The system cannot operate |
| Sign-in | Clerk on its free plan, with organizations | No usable member workspace |
| Probes | Two DigitalOcean Basic droplets in different regions: 1 vCPU, 1 GB, 25 GB, Ubuntu 24.04 (`s-1vcpu-1gb`, or `s-1vcpu-1gb-intel` where the first isn't offered). Any Linux VM with Node 22 and process supervision does | Checks and failure confirmation do not run; heartbeat monitoring also needs probes |
| Status edge | The renderer and Caddy on one of the probe droplets, which holds both, with a Cloudflare-proxied status hostname | App-hosted status routes can remain with edge redirects off; the independent status service and customer domains are unavailable |
| Workers | Cloudflare Workers Paid for heartbeat ingest, the alert sender and the watchdog, each with its own uncached Hyperdrive. The free plan can carry a small installation: it allows 100,000 Hyperdrive queries a day and five cron triggers, of which two are needed | Heartbeats, alert delivery and fleet watching don't run |
| DNS | A Cloudflare zone, free plan, for the status, ingest and sender hosts | The Workers and the edge have no hostnames |
| Email | Postmark, one server with a verified sender domain | The alert sender requires it |
| Chat alerts | A Telegram bot from BotFather, and a chat it can message for the watchdog | The sender and the watchdog require it |
| Scan suggestions | An Anthropic API key, optional | Scans use deterministic discovery without the model pass |

At list prices in October 2026 that is about $43 a month: two droplets at $6 or $7, Supabase Pro at $25 and Workers Paid at $5. The rest fits free plans. A third probe adds a third location. The hosted service runs its third as Builder-only (`PROBE_BUILDER_ONLY=true`), which with `SELF_HOSTED_PLAN=builder` still means every workspace.

Slack, Discord and signed webhook channels are additional integrations. Slack needs your own OAuth app and its paired credentials. Analytics is optional; if enabled, configure Clarity without cookies and keep both storage consents denied. Sentry and Clerk deletion webhook variables are reserved; setting them alone does not implement those features.

## The smallest installation

Everything that isn't a hosted service can share one VM: the dashboard (`npm run build`, then `npm run start`), one probe and the status edge, with one Caddy in front of the dashboard and the renderer. Give it 2 GB: the hosted service runs a probe and the edge together on 1 GB, and the dashboard comes on top. The database stays on Supabase, sign-in on Clerk and the three Workers on Cloudflare: the Workers reach the database through Hyperdrive, and a watchdog is only useful away from the machine it watches. Running Supabase itself on the same machine is untested; the app accepts a local Supabase only at an `http://localhost` address, and the Workers would need the database reachable from Cloudflare.

It works because a probe with no other location re-checks a failure from itself 20 seconds later. The cost: a problem with that machine's own network reads as your app being down, and when the machine is down, so are your dashboard and status page; the watchdog still tells you the probe stopped. That is fine for trying Staygreen or watching a few apps. For monitoring you depend on, add a second probe in another region. Off Netlify, the two POST rate rules in `netlify/edge-functions/` don't run, so put equivalent limits in front of the app.

## Set it up with a coding agent

Give the agent this repository, these three documents, the sample configurations in [`examples/`](../examples/) and one credential per provider, made for this installation:

| Provider | Credential | What the agent does with it |
|---|---|---|
| DigitalOcean | A personal access token with write scope | Creates the droplets with `doctl`, adds its SSH key and a cloud firewall |
| Supabase | An access token (`SUPABASE_ACCESS_TOKEN`) | Creates the project, links it, applies the migrations with `supabase db push`, creates the service logins in SQL and reads the API keys |
| Netlify | A personal access token (`NETLIFY_AUTH_TOKEN`) | Creates the site, sets its variables and deploys |
| Cloudflare | An API token with Workers Scripts, Hyperdrive, DNS and Workers Routes edit permissions; a second token with only Cache Purge on the status zone, which becomes `EDGE_PURGE_TOKEN` | Deploys the Workers with `wrangler`, creates the Hyperdrive configurations and every DNS record, Postmark's included |
| Clerk | The instance's publishable and secret keys | Sets them on the app and the sender |
| Postmark | The server token | Sets it on the sender and checks the domain's records |
| Telegram | The bot token | Registers the sender's webhook |

You do by hand what the providers keep in their own screens:
- Clerk's settings: organizations, membership required, sign-in, and OAuth for agent connections.
- Postmark's review of a new account.
- Creating the Telegram bot.
- Moving your domain's nameservers to Cloudflare if it isn't there yet.

Keep the credentials in a local `.env` the agent reads, never in a commit or an issue. Revoke what you no longer need once the installation runs.

A prompt to start from: *Read docs/deploying.md, docs/environment.md and docs/architecture.md. Set up Staygreen for my organization with the credentials in .env, one step of the setup order at a time, and show me each step's verification before starting the next.*

## Setup order

1. **Read and adapt the source.** Review `src/lib/plans.ts`, `src/lib/launch.ts`, site links, legal pages and branding. The source includes hosted-product defaults and copy. Set your own app, status, custom-domain and ingest host variables; replace the legal controller and policy text for your service. Location identifiers (`tor1`, `sfo3`, `fra1`, the hosted service's cloud regions) and the paid-region rule are code configuration: choose matching regions or deliberately change the model and tests together.
2. **Create the Supabase project.** Apply every file in `supabase/migrations/` in filename order with the CLI and the project named explicitly: `supabase migration list`, then `supabase db push --dry-run`, then `supabase db push`, then list again. Do not edit applied migrations. App deployment does not apply SQL. These migrations also define roles, grants, constraints and function boundaries, not just tables. Keep RLS and grant restrictions intact. A production setup needs its own migration ledger and backup/restore process.
3. **Create Clerk and configure it before onboarding.** Enable organizations, membership required and automatic first-organization creation. The current member role is `org:admin`; permission checks live in `src/lib/authz.ts`. Disable organization/account deletion paths until you implement the corresponding cleanup workflow: there is currently **no Clerk deletion webhook handler**, so leave `CLERK_WEBHOOK_SECRET` unset and arrange manual account/workspace cleanup until you implement and test signed, idempotent handling. Use Clerk's own sign-in components. Sign-in and sign-up land at `/app`; sign-out returns to `/`. Configure your instance's sign-in domains, DNS, email and legal-consent links. Use development Test mode only on disposable test resources.
4. **Skip billing.** Leave Clerk Billing off and connect no Stripe account. From the next release, set `SELF_HOSTED_PLAN=builder` on the app: every workspace gets every Builder feature at Builder's limits, and the app shows no billing screens. Until then every workspace runs on Free's limits; raise them in `limits.free` in `src/lib/plans.ts` if you need more, since the server actions pass those numbers to the database's quota checks.
5. **Configure the app.** Run `npm ci`; create your own `.env` from `.env.example` for local development, or use the host's secret store. Fill required variables from [the environment table](environment.md). Generate independent secrets for encryption, heartbeat signing and API-token hashing; never reuse another installation's values. The app validates variables at development startup and build. Run `npm run typecheck`, `npm run test:unit`, then `npm run dev`. For deployment, build with `npm run build` and use the host's Next adapter or `npm run start`; on Netlify, `netlify env:import .env` sets the variables and `netlify deploy --build --prod` deploys. Preserve CSP, origin checks, body limits and POST rate rules when moving hosts.
6. **Provision service database logins.** Create a separate login for each probe and each service with no superuser, role-creation or RLS-bypass capability. Grant only the relevant group role from the migrations: `probe`, `ingest`, `edge`, `alert_sender` or `watchdog`. The sender and edge expose restricted functions in their own schemas. Never give these services the app's Supabase secret key or a database administrator connection. Set TLS verification, password rotation and network policy deliberately; test the restricted grants against the applied schema.
7. **Deploy probes.** `npm run probe:build` bundles the runtime. Run `probe/dist/main.js` as a supervised unprivileged service. Each process needs its own database login, unique probe id, configured location and reachable peer origin, plus the shared peer HMAC secret and credential-encryption key. Set the release hash from the deployed bundle. Permit peer traffic only among the fleet and restrict administration. Peers authenticate signed requests; outbound target validation is not a substitute for a host firewall. `npm run probe:bench` is a local benchmark using test-only TLS fixtures, not a production health check. Verify registration, successful checks, independent failure confirmation, takeover and recovery. [`examples/probe/`](../examples/probe/) has the service unit, its variables and `setup.sh`, which prepares a fresh Ubuntu 24.04 box: read it before you run it.
8. **Deploy heartbeat ingest.** In `ingest/`, run `npm ci`; adapt `wrangler.toml` with your Worker name, domain and uncached Hyperdrive binding (`wrangler hyperdrive create <name> --connection-string=… --caching-disabled true`). Its connection must use the restricted ingest login. Supply `HEARTBEAT_TOKEN_KEY` through Worker secrets with the same value as the app. Review routing and rate limits, then use `npm run check` for Wrangler's dry build and deploy the explicitly reviewed configuration. The supplied sample has no production target. Verify signed pings, replay behavior, database refusal, missed-heartbeat incidents and recovery.
9. **Deploy sender and watchdog.** Prepare your own Wrangler configurations pointing at `sender/worker.ts` and `watchdog/worker.ts`, with `nodejs_compat`, distinct Worker names, separate uncached `HYPERDRIVE` bindings and minute crons. The sender needs a custom domain for `/api/telegram/webhook`; register it with Telegram using the same webhook secret as the Worker. Verify the Postmark sender/domain and supply all sender schema fields: this runtime requires both Postmark and Telegram. Set the watchdog's `WATCHDOG` namespace to the exported `Watchdog` class and add an initial `new_sqlite_classes` migration for it. Supply expected probe ids and an operator chat the bot can message. Verify delivery, retries, unsubscribe, Telegram binding, a stalled fleet and recovery. The watchdog's public HTTP handler returns 404; scheduled work runs through its binding, not a public cron URL. Start from [`examples/sender/wrangler.toml`](../examples/sender/wrangler.toml) and [`examples/watchdog/wrangler.toml`](../examples/watchdog/wrangler.toml).
10. **Deploy the status edge.** Bundle `edge/main.ts` for Node 22 with `pg-native` external, and `widget/client.ts` for the browser as `w.js`. Ship `status.css` formed from `design/tokens.css`, `design/kit.css`, `src/styles/app.css`, `src/styles/status.css` and `edge/status.css`, plus `public/icon.svg` and `src/app/fonts/Switzer-Variable.woff2`. Run the renderer with these assets in its working directory; it listens on loopback port 7080. Caddy reverse-proxies it, preserves the original Host, enables strict SNI/Host checks, and uses the app's `/api/edge/ask` for on-demand certificate authorization. Configure your status host, claim-specific custom-domain DNS targets, TLS and Cloudflare caching/purge behavior. Keep health/control handling intentional and never cache signed control requests. Verify public snapshots, unknown-host refusal, domain ownership proof, certificate issuance, cache purge and public-to-private withdrawal before setting `STATUS_EDGE_ENABLED=on` on the app. [`examples/edge/`](../examples/edge/) has the renderer's unit, its variables, the Caddyfile and `setup.sh`, which runs after the probe's on the same box; [`examples/README.md`](../examples/README.md) gives the build commands, the DNS records and the two cache rules.
11. **Verify and operate.** Run integration and browser suites only against disposable development resources after changing their explicit development-project guard. Exercise every configured channel, failure confirmation and private/public transition. Check each runtime's deployed release independently: pushing app code does not update probes, Workers or edge. Test database restoration and key backup before accepting customer data. There is no automatic deployment of this distribution.

## Agent connections

For your own deployment, configure Clerk OAuth dynamic client registration, client metadata documents without redirect-host restrictions, PKCE, JWT access tokens and audience claims. Set default scopes to `openid`, `profile`, `email`, `user:org:read`. The audience is your exact app origin plus `/mcp`. Verify discovery and a fresh sign-in against your own instance; instance cloning does not guarantee these settings carry over. Workspace membership is rechecked on requests. Workspace API tokens from the dashboard work with the REST and MCP endpoints.

The root README and registry metadata retain links to the hosted Staygreen service for existing consumers. The published npm CLI also targets that hosted API; do not assume relocating its source configures it for your installation. Adapt and test its endpoint contract before distributing a separately hosted CLI.

## Development checks and omissions

`npm run typecheck` and `npm run test:unit` are the offline export checks after `npm ci`. These do not run `next build`, which requires valid Clerk configuration, or verify a live deployment. Integration suites need Postgres/Supabase, browser suites need Clerk development accounts and browsers, live tests need network access, and go-live tests assert release readiness. Those checks are not run by the exporter.

The private operator/export tooling and its coupled unit suites are omitted: `agent-check`, `operator-database`, `probe-deploy`, `sender-worker`, `status-edge`, `staygreen-export`, `public-export` and `public-environment`. The sender and status-edge files combine runtime tests with private provisioning tests; other public unit and integration suites remain. Provisioning, secret rotation and incident-seeding scripts are not distributed; [`examples/`](../examples/) holds the files they write, as samples to adapt. Internal docs, agent instructions, generated test output and private deployment inventory are absent. Test-only TLS keys in `tests/fixtures/tls/` are public fixtures and must never be used for a deployed service.

The opt-in `tests/unit/rdap-live.test.ts` network cases are skipped in offline unit runs. The package symlink test can also skip on Windows when symlink creation is unavailable.
