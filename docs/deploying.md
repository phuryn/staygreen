# Deploying Staygreen

This is a multi-service system. You must configure identity, billing, database privileges, DNS, TLS, independent check runners, scheduled Workers and alert delivery. There is no one-click deployment, bundled production infrastructure, or automatic migration step. Use separate development and production resources and verify each boundary before accepting real monitoring traffic.

## What you need

| Part | Requirement | If omitted |
|---|---|---|
| Dashboard | Node 22+ Next.js App Router host with server actions and route handlers; `netlify.toml` and the two `netlify/edge-functions/` POST rate rules are supplied | No member dashboard, configuration or hosted agent API |
| Database | Supabase Postgres, all ordered migrations, backups and restricted service logins | The system cannot operate |
| Identity and billing | Clerk sign-in, organizations and organization billing plans | No usable member workspace; absent paid features fall back to free limits |
| Probes | A small fleet of Linux VMs in at least two regions, with Node 22, controlled peer connectivity and process supervision | Checks and failure confirmation do not run; heartbeat monitoring also needs probes |
| Status edge | A Linux VM running the renderer and Caddy, with a Cloudflare-proxied status hostname | App-hosted status routes can remain with edge redirects off; independent status service and customer domains are unavailable |
| Heartbeat ingest | Cloudflare Worker and uncached Hyperdrive using the ingest role | Heartbeat URLs do not receive pings; do not offer heartbeat monitors |
| Alert sender | Separate Cloudflare Worker, uncached Hyperdrive, minute cron, Postmark and Telegram | Delivery work is not sent; incidents and status pages still update |
| Watchdog | Independent Cloudflare Worker, uncached Hyperdrive, minute cron, SQLite Durable Object and operator Telegram chat | Fleet failures have no independent notification |
| Scan suggestions | Optional Anthropic key | Scans use deterministic discovery without the model pass |

Slack, Discord and signed webhook channels are additional integrations. Slack needs your own OAuth app and its paired credentials. Analytics is optional; if enabled, configure Clarity without cookies and keep both storage consents denied. Sentry and Clerk deletion webhook variables are reserved; setting them alone does not implement those features.

## Setup order

1. **Read and adapt the source.** Review `src/lib/plans.ts`, `src/lib/launch.ts`, site links, legal pages and branding. The source includes hosted-product defaults and copy. Set your own app, status, custom-domain and ingest host variables; replace the legal controller and policy text for your service. Location identifiers (`tor1`, `sfo3`, `fra1`, the hosted service's cloud regions) and the paid-region rule are code configuration: choose matching regions or deliberately change the model and tests together.
2. **Create Supabase development resources.** Apply every file in `supabase/migrations/` in filename order using a migration tool with an explicitly selected database. Do not edit applied migrations. Compare the remote ledger before deploying code: app deployment does not apply SQL. These migrations also define roles, grants, constraints and function boundaries, not just tables. Keep RLS and grant restrictions intact. A production setup needs its own migration ledger and backup/restore process.
3. **Create Clerk and configure it before onboarding.** Enable organizations, membership required and automatic first-organization creation. The current member role is `org:admin`; permission checks live in `src/lib/authz.ts`. Disable organization/account deletion paths until you implement the corresponding cleanup workflow. Use Clerk's own sign-in components. Sign-in and sign-up land at `/app`; sign-out returns to `/`. Configure your instance's sign-in domains, DNS, email and legal-consent links. Use development Test mode only on disposable test resources.
4. **Configure organization billing.** Create Free and Builder organization plans, not user plans. `src/lib/plans.ts` maps the entitlement slugs `scale_builder`, `white_label`, `private_pages`, `subscribers`, `alert_rules`, `history_1y` and `notify_teammates` to limits. Preserve exact entitlement slugs and include them in session tokens. Do not attach features to permissions: a failed payment must not change who can administer a workspace. `scripts/clerk/billing.json` records the plan/feature shape and display fields; review its prices and copy for your deployment. The app reads verified Clerk features and needs no subscription table or payment webhook. There is currently **no Clerk deletion webhook handler**: leave `CLERK_WEBHOOK_SECRET` unset and arrange manual account/workspace cleanup until you implement and test signed, idempotent handling.
5. **Configure the app.** Run `npm ci`; create your own `.env` from `.env.example` for local development, or use the host's secret store. Fill required variables from [the environment table](environment.md). Generate independent secrets for encryption, heartbeat signing and API-token hashing; never reuse another installation's values. The app validates variables at development startup and build. Run `npm run typecheck`, `npm run test:unit`, then `npm run dev`. For deployment, build with `npm run build` and use the host's Next adapter or `npm run start`. Preserve CSP, origin checks, body limits and POST rate rules when moving hosts.
6. **Provision service database logins.** Create a separate login for each probe and each service with no superuser, role-creation or RLS-bypass capability. Grant only the relevant group role from the migrations: `probe`, `ingest`, `edge`, `alert_sender` or `watchdog`. The sender and edge expose restricted functions in their own schemas. Never give these services the app's Supabase secret key or a database administrator connection. Set TLS verification, password rotation and network policy deliberately; test the restricted grants against the applied schema.
7. **Deploy probes.** `npm run probe:build` bundles the runtime. Run `probe/dist/main.js` as a supervised unprivileged service. Each process needs its own database login, unique probe id, configured location and reachable peer origin, plus the shared peer HMAC secret and credential-encryption key. Set the release hash from the deployed bundle. Permit peer traffic only among the fleet and restrict administration. Peers authenticate signed requests; outbound target validation is not a substitute for a host firewall. `npm run probe:bench` is a local benchmark using test-only TLS fixtures, not a production health check. Verify registration, successful checks, independent failure confirmation, takeover and recovery.
8. **Deploy heartbeat ingest.** In `ingest/`, run `npm ci`; adapt `wrangler.toml` with your Worker name, domain and uncached Hyperdrive binding. Its connection must use the restricted ingest login. Supply `HEARTBEAT_TOKEN_KEY` through Worker secrets with the same value as the app. Review routing and rate limits, then use `npm run check` for Wrangler's dry build and deploy the explicitly reviewed configuration. The supplied sample has no production target. Verify signed pings, replay behavior, database refusal, missed-heartbeat incidents and recovery.
9. **Deploy sender and watchdog.** Prepare your own Wrangler configurations pointing at `sender/worker.ts` and `watchdog/worker.ts`, with `nodejs_compat`, distinct Worker names, separate uncached `HYPERDRIVE` bindings and minute crons. The sender needs a custom domain for `/api/telegram/webhook`; register it with Telegram using the same webhook secret as the Worker. Verify the Postmark sender/domain and supply all sender schema fields: this runtime requires both Postmark and Telegram. Set the watchdog's `WATCHDOG` namespace to the exported `Watchdog` class and add an initial `new_sqlite_classes` migration for it. Supply expected probe ids and an operator chat the bot can message. Verify delivery, retries, unsubscribe, Telegram binding, a stalled fleet and recovery. The watchdog's public HTTP handler returns 404; scheduled work runs through its binding, not a public cron URL.
10. **Deploy the status edge.** Bundle `edge/main.ts` for Node 22 with `pg-native` external, and `widget/client.ts` for the browser as `w.js`. Ship `status.css` formed from `design/tokens.css`, `design/kit.css`, `src/styles/app.css`, `src/styles/status.css` and `edge/status.css`, plus `public/icon.svg` and `src/app/fonts/Switzer-Variable.woff2`. Run the renderer with these assets in its working directory; it listens on loopback port 7080. Caddy reverse-proxies it, preserves the original Host, enables strict SNI/Host checks, and uses the app's `/api/edge/ask` for on-demand certificate authorization. Configure your status host, claim-specific custom-domain DNS targets, TLS and Cloudflare caching/purge behavior. Keep health/control handling intentional and never cache signed control requests. Verify public snapshots, unknown-host refusal, domain ownership proof, certificate issuance, cache purge and public-to-private withdrawal before setting `STATUS_EDGE_ENABLED=on` on the app.
11. **Verify and operate.** Run integration and browser suites only against disposable development resources after changing their explicit development-project guard. Exercise every configured channel, failure confirmation and private/public transition. Check each runtime's deployed release independently: pushing app code does not update probes, Workers or edge. Test database restoration and key backup before accepting customer data. There is no automatic deployment of this distribution.

## Agent connections

For your own deployment, configure Clerk OAuth dynamic client registration, client metadata documents without redirect-host restrictions, PKCE, JWT access tokens and audience claims. Set default scopes to `openid`, `profile`, `email`, `user:org:read`. The audience is your exact app origin plus `/mcp`. Verify discovery and a fresh sign-in against your own instance; instance cloning does not guarantee these settings carry over. Workspace membership is rechecked on requests. Workspace API tokens from the dashboard work with the REST and MCP endpoints.

The root README and registry metadata retain links to the hosted Staygreen service for existing consumers. The published npm CLI also targets that hosted API; do not assume relocating its source configures it for your installation. Adapt and test its endpoint contract before distributing a separately hosted CLI.

## Development checks and omissions

`npm run typecheck` and `npm run test:unit` are the offline export checks after `npm ci`. These do not run `next build`, which requires valid Clerk configuration, or verify a live deployment. Integration suites need Postgres/Supabase, browser suites need Clerk development accounts and browsers, live tests need network access, and go-live tests assert release readiness. Those checks are not run by the exporter.

The private operator/export tooling and its coupled unit suites are omitted: `agent-check`, `operator-database`, `probe-deploy`, `sender-worker`, `status-edge`, `staygreen-export`, `public-export` and `public-environment`. The sender and status-edge files combine runtime tests with private provisioning tests; other public unit and integration suites remain. Provisioning, secret rotation and incident-seeding scripts are not distributed. Internal docs, agent instructions, generated test output and private deployment inventory are absent. Test-only TLS keys in `tests/fixtures/tls/` are public fixtures and must never be used for a deployed service.

The opt-in `tests/unit/rdap-live.test.ts` network cases are skipped in offline unit runs. The package symlink test can also skip on Windows when symlink creation is unavailable.
